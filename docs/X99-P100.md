# X99 with two or three Tesla P100s

The IQ3_S engine splits every selected expert across all active cards. Its 640 intermediate columns occupy twenty quantization blocks. Two cards take ten blocks each. Three take seven, seven and six (224/224/192 columns). The down-projection kernel handles the final 32 columns of each 224-column slice. The three-card profile uses the general prompt path and lets the engine size its expert cache to available VRAM.

[X99 and developer benchmark figures](X99-RESULTS.md) · [Rust engine measurements](X99-RUST.md)

## Build and prepare

From the repository root, choose the number of cards for the session. Use a separate build directory for each count. The two configurations can share prepared model files on NVMe.

```bash
export CARDS=3                          # Set to 2 for the two-card run
export CUDA=/usr/local/cuda-12.9
export HOSTCXX=/usr/bin/g++-13
export B="$PWD/build/$CARDS"
export DATA=/path/on/nvme/flash-next
export LD_LIBRARY_PATH="$CUDA/lib64${LD_LIBRARY_PATH:+:$LD_LIBRARY_PATH}"

bash build.sh
bash setup.sh "$DATA"
PROFILE="$DATA/profile.json"
if [ "$CARDS" = 3 ]; then PROFILE="$DATA/profile-3gpu.json"; fi
bash run.sh "$DATA" --config "$PROFILE" --port 18080
```

Setup keeps existing profiles. Check the executable and GPU indices in the selected JSON when reusing a data directory. The measurements use the full model, a 524,288-token context, MTP, lookup 15 and exact routing.

## Reproduce the timing

Run this in a second shell with the same DATA value. Start each comparison with a freshly loaded model and keep the API idle apart from the benchmark.

```bash
python3 bench/bench.py --strata-dir "$DATA/strata-v0.2.9" \
  --url http://127.0.0.1:18080 --wait 6 --ours iq3_s \
  --tests fresh,edit,long,medium,image --out "$DATA/benchmark-$CARDS.json"
```

## GPU regression

With the same build environment as above, build the optional test. It compares compact and zero-padded down projections for four weight formats, including the 192- and 224-column slices. A 96-row build exercises 392 cases.

```bash
cmake -S . -B "$B" -DSTRATA_BUILD_TESTS=ON
cmake --build "$B" --target split_p100_tail_test -j 2
"$B/split/split_p100_tail_test"
"$CUDA/bin/compute-sanitizer" --tool memcheck --error-exitcode 1 "$B/split/split_p100_tail_test"
```

## Optional two-card lookup experiment

Set `FNX_LOOKUP_SOURCES` to `"4"` in the profile's `env` object to search the last four matching trigrams. The engine chooses the candidate with the longest matching history that agrees with the first draft token. Equal lengths favor the newest occurrence. The default of one source reproduces the upstream lookup policy. This experiment keeps the existing verifier and lookup length. It adapts the selection rule from [Basalt's suffix drafter](https://github.com/jesdga95/basalt/blob/899e820af777705cd29b35b1deb8612f24c42c5e/src/spec/suffix_drafter.cpp).

## Measured PCIe traffic on X99

Two simultaneous pinned host-to-device transfers delivered 5.97 and 5.96 GB/s of payload to two Gen3 ×8 cards. The developer reports 11.9 GB/s per Gen3 ×16 card. The X99 engine assigned 29.0 GiB of routed expert weights to host RAM on two cards and 17.9 GiB on three cards. Both measurements used the full IQ3_S model and two guessed experts per row. [Developer's test system](https://github.com/Megla123/qwen3.8-flash-next-2x-p100/tree/404de0a78ac044eef53fed8b46dd76639e29d089#the-machine)

| Two-card workload | GPU 0 samples at ≥90% of calibrated RX | GPU 1 samples at ≥90% of calibrated RX |
|---|---:|---:|
| Fresh writing | 11 / 113 (10%) | 13 / 127 (10%) |
| Python and Markdown edits | 14 / 151 (9%) | 17 / 147 (12%) |
| Long prefill | 23 / 61 (38%) | 24 / 65 (37%) |
| Medium prefill series | 74 / 132 (56%) | 72 / 130 (55%) |

Counts pool two newly loaded runs. Each denominator counts valid samples from the indicated workload. The GPU-side calibration medians were 6,278 and 6,274 MB/s. Samples above the theoretical one-way link limit were discarded, including 48 out of 346 raw edit samples across both cards. The counter covers short intervals sampled once per second, so the proportions describe observations. [NVIDIA's PCIe counter documentation](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html)

## Reproducing the X99 profiles

Each comparison used a newly loaded engine. To reproduce the two-card tests on the exact code, use the [two-card-only branch](https://github.com/Kenzu/qwen3.8-flash-next-2x-p100/tree/basalt-2p100). Its original four-source experiment is commit `9448e85`; this is the two-card baseline engine plus the lookup change. Three-card timings came from the three-card port on the same upstream pin. The published three-card kernel at `c43e4b8` separately passed 392 compact-versus-padded GPU cases and compute-sanitizer. All comparisons use Megla's benchmark inputs from `404de0a`.

Apply these overrides in the profile JSON's `env` object. The lookup-source and extension settings take effect in a binary built with the respective change.

| Profile feature | Overrides relative to the two-card baseline |
|---|---|
| Two prefetch guesses | `FNX_PREFETCH_WANT=2` |
| Six prefill blocks per pass | `FNX_PF_PASS=6`, `FNX_PF_TAIL_MIB=3750`, `FNX_CKPT_EVERY=24576` |
| Four lookup sources | `FNX_LOOKUP_SOURCES=4` |
| Longer proposals on strong matches | `FNX_LOOKUP_EXTEND_MIN=8` on top of four sources |

The six-block setting groups up to six 4,096-token chunks per pass. The larger scratch reservation and 24,576-token checkpoint spacing allow that pass size. A revised long prompt can require more recomputation between checkpoints. For three cards, start with the separate three-card profile and set `FNX_PREFETCH_WANT=2` to reproduce its reported run.

On the X99, a separate six-thread RAM test using the unmodified STREAM 5.10 code measured 53.2 GB/s copy and 35.3 GB/s triad with 64 million doubles per array, 20 repetitions and thread affinity set to physical cores. These are host-memory microbenchmarks. [STREAM source](https://www.cs.virginia.edu/stream/FTP/Code/stream.c)

## Screening the next lookup change

A CPU replay used the actual edit prompts and the text returned by the four-source engine. It searched at every output position, supplying the known next token. Adding up to four older eight-token matches to the four trigram candidates yielded a longer correct continuation at 33 of 1,192 Python positions and 33 of 1,227 Markdown positions. These are counts of overlapping positions in retokenized visible text. Actual draft tokens and verifier timing require an engine trial. [Basalt's eight-token index](https://github.com/jesdga95/basalt/blob/899e820af777705cd29b35b1deb8612f24c42c5e/include/basalt/spec/suffix_drafter.hpp)
